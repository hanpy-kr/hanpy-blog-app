# Relational to Document Model with MongoDB

*관계형 모델을 문서 모델로 전환하고, 효율적인 데이터 설계를 배우다*

---

## 들어가며

데이터베이스는 애플리케이션의 심장과 같습니다.
과거에는 \*\*관계형 데이터베이스(RDB)\*\*가 대부분의 시스템을 지탱했지만, 오늘날 서비스는 더 복잡해지고 데이터 형태도 다양해졌습니다.
소셜 네트워크 피드, IoT 센서 로그, 전자상거래 장바구니처럼 구조가 끊임없이 변하는 데이터를 다루려면, **고정된 스키마**만으로는 한계가 있습니다.

MongoDB는 **Document-Oriented Database**로, JSON과 유사한 문서(document)에 데이터를 저장합니다.
이는 **스키마의 유연성**, **개발자 친화적 데이터 구조**, **클라우드 네이티브 운영 방식**을 가능하게 합니다.

이번 글에서는 다음을 다룹니다:

1. 관계형 모델을 문서 모델로 변환하는 방법
2. 다양한 관계(One-to-One, One-to-Many, Many-to-Many) 설계 방법
3. 스키마 검증을 통해 데이터 무결성 유지하기
4. MongoDB Atlas에서 실습 및 운영 적용

---

## 1. Model for Workloads (워크로드 기반 모델링)

### 1.1 관계형 모델 vs 문서 모델 매핑

* **SQL 테이블(Table)** → **MongoDB 컬렉션(Collection)**
* **행(Row)** → **문서(Document)**
* **열(Column)** → **필드(Field)**

```sql
-- SQL 예시: 사용자 테이블
CREATE TABLE users (
  id INT PRIMARY KEY,
  name VARCHAR(100),
  email VARCHAR(255)
);
```

```json
// MongoDB 문서 예시: 사용자 컬렉션
{
  "_id": ObjectId("..."),
  "name": "Alice",
  "email": "alice@example.com"
}
```

MongoDB에서는 데이터 구조를 미리 강제하지 않기 때문에, `users` 컬렉션 안의 문서마다 **필드 구성이 달라도 허용**됩니다.

---

### 1.2 워크로드 기반 설계

MongoDB 모델링의 핵심은 \*\*워크로드(Read/Write 패턴)\*\*에 맞춰 설계하는 것입니다.

* **읽기 위주 쿼리**가 많다면?
  → 관련 데이터를 하나의 문서에 **Embedding(내장)**

* **쓰기/갱신이 자주 발생**한다면?
  → 데이터를 나누어 **Referencing(참조)**

👉 관계형 DB의 “정규화”와 달리, MongoDB는 **쿼리 성능과 데이터 접근 패턴**을 우선합니다.

---

## 2. Design Relationships (데이터 관계 설계)

### 2.1 Embedding vs Referencing

* **Embedding (내장)**

  * 관련 데이터를 한 문서 안에 저장
  * 장점: 읽기 속도 빠름 (한 번의 조회로 해결)
  * 단점: 중복 데이터가 많을 수 있음

* **Referencing (참조)**

  * 다른 컬렉션의 `ObjectId`를 저장
  * 장점: 데이터 중복 최소화
  * 단점: 조회 시 `lookup` 필요 → 성능에 영향 가능

---

### 2.2 관계별 모델링 예시

#### One-to-One

```json
// 사용자와 프로필 (Embedding)
{
  "name": "Alice",
  "profile": { "age": 29, "bio": "Hello MongoDB" }
}
```

#### One-to-Many

```json
// 사용자와 주문 (Referencing)
{
  "name": "Alice",
  "orders": [
    ObjectId("order1_id"),
    ObjectId("order2_id")
  ]
}
```

#### Many-to-Many

```json
// 학생과 강좌 (Cross Reference)
students = { "_id": 1, "name": "Alice", "courses": [101, 102] }
courses  = { "_id": 101, "title": "Database Design", "students": [1, 2, 3] }
```

👉 선택 기준:

* **자주 함께 조회되는 데이터** = Embedding
* **자주 갱신되거나 독립성이 중요한 데이터** = Referencing

---

## 3. Validate Schemas (스키마 검증)

MongoDB는 스키마리스(schema-less)로 유명하지만, 실제 서비스에서는 **데이터 무결성**이 중요합니다.
이를 위해 **Schema Validation** 기능을 제공합니다.

---

### 3.1 스키마 검증 필요성

* API 입력값 실수 방지
* 데이터 구조 일관성 보장
* 특정 필드가 반드시 존재하도록 강제

---

### 3.2 JSON Schema 예시

`reviews` 컬렉션에 다음 규칙을 강제한다고 가정합니다:

* `username`: 문자열, 필수
* `rating`: 정수 0\~5 범위, 필수
* `comments`: 배열, 최대 3개 요소, 필수

```json
{
  "bsonType": "object",
  "required": ["username", "rating", "comments"],
  "properties": {
    "username": { "bsonType": "string" },
    "rating": { "bsonType": "int", "minimum": 0, "maximum": 5 },
    "comments": { "bsonType": "array", "maxItems": 3 }
  }
}
```

---

### 3.3 스키마 적용하기

```js
db.createCollection("reviews", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["username", "rating", "comments"],
      properties: {
        username: { bsonType: "string" },
        rating: { bsonType: "int", minimum: 0, maximum: 5 },
        comments: { bsonType: "array", maxItems: 3 }
      }
    }
  }
});
```

👉 이렇게 설정하면 잘못된 데이터가 삽입되려 할 때 MongoDB가 자동으로 거부합니다.

## 4. MongoDB Atlas 활용

### 4.1 Atlas란?

MongoDB Atlas는 \*\*클라우드에서 제공되는 DBaaS(Database as a Service)\*\*입니다.
사용자는 서버 설치, 보안 패치, 백업 등을 신경 쓸 필요 없이, UI에서 몇 번의 클릭으로 클러스터를 배포할 수 있습니다.

---

### 4.2 Atlas 주요 기능

* **샘플 데이터 로드**: 간단히 데이터를 불러와 CRUD 실습
* **자동 Failover**: 특정 가용 영역이 장애 나도 다른 노드로 자동 전환
* **실시간 모니터링**: Real-Time Performance Panel로 쿼리, 네트워크, CPU 모니터링
* **보안 기능 내장**: RBAC, 다중 인증(MFA), IP 화이트리스트

👉 직접 운영하는 MongoDB보다 **운영 부담이 크게 줄어듭니다.**

---

## 마치며

MongoDB로 전환한다는 건 단순히 SQL을 JSON으로 바꾸는 게 아닙니다.

* **워크로드 중심의 설계 철학**을 이해해야 하고,
* **관계 설계 방식**(Embedding vs Referencing)을 올바르게 선택해야 하며,
* **스키마 검증**을 통해 데이터 무결성을 유지해야 합니다.

MongoDB Atlas까지 활용하면, 클라우드 환경에서 **운영 자동화 + 확장성**까지 확보할 수 있습니다.

---

## 요약

* Document Model: JSON-like 구조, 유연한 스키마
* Model for Workloads: 읽기/쓰기 패턴에 맞춘 설계
* Design Relationships: Embedding ↔ Referencing 전략적 선택
* Validate Schemas: JSON Schema로 데이터 무결성 강화
* Atlas: 관리형 클라우드 MongoDB, 운영 부담 최소화
